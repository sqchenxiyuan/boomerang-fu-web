# 地图扩展：设计、实现与验证

日期：2026-10-28。先完成设计准备，待机制、手感、过场分析提供证据后实施。当前五张地图、角色与飞镖传送、寻路和地图选择/轮换均已接入；模拟验证结果见文末，浏览器视觉验收由整体验收记录覆盖。

目标是在现有山间庭院之外增加至少四张有不同战术结构的地图，并保证人物、飞镖、AI、渲染与未来 SDK 读取的是同一份权威场景状态。布局、名称、美术及下文的数值均为本项目设计，不宣称精确复原原版地图。

现有六张预览已人工查看：LevelEnclosed 是较开阔的围合场地，LevelCrate 中有大量分散箱体，LevelTeleportals 有迷宫墙和成对门，LevelFalling 有水面上的地砖块，LevelRaftPair 有成对平台。这里只使用结构启发，不复制资源或声称贴图足以还原完整场景。

## v1 基线中发现的依赖

下面记录分析时的 v1 问题；地图数据化、导航边界与缓存、场景重建已在本轮修正。几何统一入口继续保留。

- `src/core/arena.ts` 只有无参数的 `createArena()`，所有地图数据直接构造；`Arena` 尚无 ID、显示名称、主题或机关。
- `src/simulation/state.ts` 的新局与每回合重置均调用同一工厂；出生点按 actor ID 索引。选图与轮换必须在这里统一，不能只让菜单换背景。
- `src/simulation/navigation.ts` 的网格固定为 `x=-11..11`、`y=-7..7`。它需要从地图边界生成，并对所有边做半径余量、扫掠墙碰撞和水域采样检查。当前最终网格节点也未要求直通真正目标，应在重构时补齐。
- `src/rendering/renderer.ts` 只在构造时创建 `ArenaView`，`reset()` 只重建人物等对象。换图必须销毁旧场景、创建新场景；同图新回合也要恢复已破坏物的显示。
- `src/rendering/arena-view.ts` 的边石、植物、旗帜、路石和外围岛屿使用庭院固定坐标。应从主题与地图 bounds 派生，装饰不能在水坑上做出可行走假象。
- `traceObstacles`、`moveAndSlide`、`onGround` 已共享模拟几何，是值得保留的统一入口。地图设计不另造渲染专用碰撞。
- 当前决胜圈以 `(0,0)` 为圆心；地图必须保留可达的中心陆地。今后若做环形水坑地图，须先引入经过可达性检查的决胜点。

## 五张地图的具体分工

首批统一保持约 `26 × 16.4` 世界单位的外边界，继续支持 2–4 人；人物半径目前 `0.47`。主要双向通道净宽至少 `2.4`，单向风险捷径也不小于 `1.6`。这些是设计约束，不是原版测量值。

| ID / 名称 | 核心结构 | 主要战术与可观察差异 | 风险与验收重点 |
| --- | --- | --- | --- |
| `courtyard` 山间庭院 | 保留中央喷泉、两侧水坑、斜向墙和少量箱体 | 作为开阔程度中等的基准图，绕中心追逐与反弹 | 回归现有所有机制测试；不因数据化改变旧图尺寸 |
| `canal` 双桥水道 | 中央竖向水道在 `y=-2.8..-1.2` 和 `y=1.2..2.8` 留两条陆桥；中央 `(0,0)` 留独立横向陆地连接，避免决胜点落水。桥头短墙错位，两端有宽陆地绕行区 | 横跨水面投掷更直接，步行需选桥，冲刺可切水道；桥头近战与远射有不同收益 | 水道分成互不重叠矩形坑；保持至少两条常规走路通路，不要求机器人靠冒险冲刺才能接敌 |
| `market` 货箱集市 | 四组低矮石摊位形成交错射线，六至十个箱子分布在中部捷径，外围主环路始终畅通 | 开局曲射与掩体重要；破箱后出现新近路和远射路线，后半回合明显更开放 | 未破箱时各出生点已经连通；破箱后 LOS、导航和渲染同一 tick 生效；爆炸遮挡仍按事件前的状态结算 |
| `switchback` 折返回廊 | 两组平行长墙各留相反端开口，中心有横向穿道，外围有第二绕行路线；少量箱体可缩短一条路线 | 强调贴墙反弹、转角伏击与无镖时撤退；与开放图相比会产生更长路径和较少直射机会 | 无宽度小于身体直径的死缝；长墙不能把出生点隔死；AI 不能用朝敌方直走的回退路径撞墙 |
| `portals` 跃迁花园 | 三条墙廊和开放中心，西南/东北各一座同色门作为第一对，西北/东南可添加第二对；两侧至少保留普通走路绕行路线 | 绕过长墙、快速换边、从另一方向发起攻击；门口成为可争夺的危险点 | 首批机关选传送门；门口/出口不得在水上、墙内或出生点；AI 至少在一个验证场景主动选择门路径 |

`canal` 的名称代表水道与桥路线，具体矩形分割在实现时以几何连通测试为准。不得为了通过测试悄悄去掉水道、箱体或传送门，地图的结构特征需要进入断言和截图验收。

## 数据与状态结构

当前实现集中在 `src/core/arena.ts`：`MAPS` 保存只读目录/显示元数据，`createArena(id)` 每次构造独立运行态，`mapInfo(id)` 查询元数据，`selectRoundMap(first, rotation, round)` 确定性选图。渲染使用元数据取色，地图规则不导入 Three.js、DOM 或音频。下方示意表达数据职责，实际导出接口以 `src/core/types.ts` 和 `arena.ts` 为准。

```ts
type MapId = 'courtyard' | 'canal' | 'market' | 'switchback' | 'portals';

interface MapDefinition {
  id: MapId;
  name: string;
  subtitle: string;
  description: string;
  theme: 'garden' | 'canal' | 'sandstone' | 'ruins';
  halfWidth: number;
  halfHeight: number;
  obstacles: readonly ObstacleDefinition[];
  pits: readonly Pit[];
  spawns: readonly Vec2[];
  pickupSpawns: readonly Vec2[];
  portals: readonly PortalDefinition[];
}

interface PortalDefinition {
  id: string;
  exitId: string;
  position: Vec2;
  exitDirection: Vec2;
  radius: number;
}

// 实际字段形状在机制分析后确定；外部消费者依赖稳定 ID。
interface Arena {
  id: MapId;
  revision: number;
  // 保留现有 halfWidth / halfHeight / obstacles / pits / spawns / pickupSpawns。
  portals: PortalDefinition[];
}
```

地图目录是不可变模板；`broken`、机关计时、实体传送锁定属于运行态。两个 Game 实例不得共享障碍对象或 Vec2 引用。`revision` 只在导航拓扑改变时增加，供寻路缓存失效；轮换换图本身也有新的 Arena 对象。

人物与飞镖的传送锁定可各有 `portalCooldown` 和 `lastPortalId`；不宜放在可全局复用的地图模板上。若采用通用 `portalLocks` 表，也必须位于 Arena 运行态并区分 actor/disc ID，不能污染地图定义。

## 传送门的实现与已知边界

补充读取 `Teleportal`、`Actor`、`Projectile` 和 `AI` 后，已确认原版人物与飞镖均可传送，速度方向不在该分支旋转，并禁止两渲染帧再次触发。Web 实现遵循这个方向，固定步长下采用两个模拟 tick；这是时间基准的明确差异。

1. 门有明确入口半径、配对出口和朝向；地图保证出口前方有安全落点。玩家接触触发，倒计时和结算时不触发。
2. 角色用移动线段与入口圆相交，避免高速冲刺直接跳过门。若路径在撞墙后被裁切，只检测实际可达线段；传送门不得穿透更早发生的墙碰撞。
3. 飞镖已支持过门，和墙、人物碰撞按最早 `t` 合并选择；同 tick 的冷却禁止连跳，出口继续处理剩余位移。掉落镖不自动传送。
4. 出口按朝向偏移 `radius + entityRadius + 0.08`，同时用 `safePosition` 核验。与已读取的原版分支一致，保持实体方向、速度、冲刺方向和飞镖归属，不额外旋转。Web 的圆形门半径和 0.08 偏移余量是设计值。
5. 出口 `previous` 与 `position` 同步，禁止插值时横跨整张地图。发 `teleport` 事件，包含入口、出口、实体类型及 ID，让显示/音频独立响应。
6. 使用两个模拟 tick 的实体锁定，并要求从门触发范围外向内跨越；站在门中心不重复传送。完整机器人比赛另外暴露了双方每六 tick 互相追门的循环，AI 现增加 0.65 秒沿出口朝向离门，再恢复追踪；此行为明确属于 Web 调整。
7. 出口被角色占据时进行普通人物分离；出口与静态障碍重叠则本次不传送。当前没有额外的随机出口选点或传送伤害。
8. 瞬移不构成横跨入口到出口的伤害射线；传送后通常的近战/飞镖命中仍按当前位置判定，且不绕过原有护盾、冲刺和无敌规则。

选择传送门可先解决离散拓扑变化。周期滑墙需要额外处理连续相对碰撞、挤压伤害、实体推出与时变路径，不和首批地图混成一个未经验证的机关系统。

## 选择、轮换与回合过场

`MatchOptions` 已增加可选 `mapId` 与 `mapRotation: 'fixed' | 'cycle'`，默认庭院与固定；固定选择会传入 Game，SDK 使用同一入口。轮换顺序保留所选图为起点，其余按目录顺序循环。当前没有随机轮换，不消耗战斗 RNG。

菜单展示地图名字与一句战术提示；主菜单背景也可以预览当前地图，但不能提前启动比赛模拟。HUD 的回合条显示真实当前地图。轮换只在回合重置时切换，活着/飞行中的战斗阶段不得换场景。

过场顺序：回合结算计分 → 显示下一张地图名 → 遮罩过渡/短暂镜头拉远 → 在完全遮挡的节点重置模拟与场景 → 倒计时与角色入场 → 恢复输入。具体时序由过场分析统一负责；地图层不自行创建第二套计时器。暂停冻结战斗与过场时间，恢复不能吞/重复一次轮换。

新回合保持现有分数、击杀数、持久强化；清空飞镖、拾取物、传送锁定和导航缓存，恢复所有箱体。当前按 actor ID 稳定分配出生点，两人局使用对角点，四人局使用四个不同点；出生点公平性尚未做大规模统计，不宣称布局达到竞技平衡。

## 碰撞、AI 与渲染一致性

### 几何与导航

- 地面仍由外矩形减去非重叠矩形水坑组成。桥作为未被坑覆盖的地面，不额外放一块只供显示的桥面。
- 网格从真实 bounds 生成，步长 `1.0`，传送入口和实际出口增加明确节点；缓存跟随 Arena 身份、revision 与箱体破坏状态失效。
- 常规路径节点与线段用 `playerRadius + 0.13` 检查，斜边不得穿角；墙边合法角色可先用身体半径连接到安全网格，避免因额外余量丢失路径。安全目标的末段也检查可达；危险/墙内目标取邻近安全节点。
- 传送门为有向特殊边，返回的路径节点必须保留“进入哪扇门”的语义。路径平滑不能把传送边当作普通直线，再用 LOS 抹掉这次传送。
- 有传送边时欧氏距离可能高估剩余代价，因此使用 `h=0` 的 Dijkstra；无门采用 A*。`NavigationWaypoint.portalId/viaPortal` 与 `advancePath` 保留特殊边语义。
- 破箱更新导航 revision，机器人在下一次决策时重算；门后位置变化也清除旧路径。无路时停留/找安全方向，不默认直冲敌人穿墙。
- AI 冲刺不仅核验终点，还沿路径检查水面长度、墙与落点；正常导航永远存在不必跳水的接敌通路。

### 显示

- renderer 按地图 ID 与回合号切场景，释放原几何及场景独享材质；显式重开会重置此标记。SDK 每帧返回新的快照对象，不以对象引用变化重复重建地图。地图切换测试关注连续轮换的几何/纹理计数，不能只检查第一张图看起来正确。
- 地面孔洞与 `onGround` 使用相同数据，墙与箱体尺寸来自 obstacle 半尺寸；高度和装饰只能改变视觉，不能默默改变水平碰撞体。
- 每个传送门有相同配对颜色和清楚朝向，入口触发圈可见，出口闪光/粒子仅消费模拟事件。机器人可以使用门时人类也应读懂去向。
- 保留现有俯视透视相机，取景由地图 bounds 和宽高比计算，确保 960×640 下也能看全四个出生点与门口；前景装饰不遮挡关键路线。

| 资源与 SDK 兼容 | 不用原版文件也能运行；两场实例地图运行态不串改；重复切图释放场景；不经 DOM 也能完成全机器人测试 | 生产构建、离线本地资源检查、隔离实例测试和渲染资源统计 |

地图测试全过只能证明这组原创地图和机关按 Web 约定工作，不能替代原版手感与逐帧实机校准。完成报告应把“静态证据确认的原版能力”“本项目采用的规则”“实际已跑过的验证”分开说明。

## 建议实施顺序

1. 机制/手感/过场分析确定门交互及统一过场接口后，再动源码。
2. 数据化庭院，新增地图 ID 与工厂，修正导航 bounds 和场景重建，回归旧图。
3. 实现水道、市场、回廊，先跑出生点/路径/完整机器人对局，检查真实几何瓶颈。
4. 实现门状态、路径边与门图，跑独立交互用例，再观察完整对局中实际使用门。
5. 接入菜单选择、轮换和过场，做五图浏览器截图、资源释放和生产构建检查。
6. 将稳定地图目录、选图参数、快照和事件纳入后续 SDK；SDK 不需要了解 Three.js 场景对象。
